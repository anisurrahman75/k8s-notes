# **5. Zombie Reaping and the `init` Problem**

← [4.pid1-semantics.md](4.pid1-semantics.md) | next → [6.debugging.md](6.debugging.md)

---

## **The mechanism**

When a process dies, its exit status stays in the kernel as a **zombie** until its parent calls `wait()`. If the parent died first, the orphan is reparented to **PID 1 of its namespace** — and PID 1 must reap it.

Real `init` systems loop on `wait()` forever. `sleep`, `nginx`, `java -jar app.jar`, and most application binaries do not.

```
  parent dies
       │
  orphan reparented ──► PID 1
                          │
                    calls wait()?  ── no ──► ZOMBIE forever (PID slot leaked)
                          │
                         yes ──────────────► reaped, slot freed
```

---

## **Demo: a non-reaping PID 1 accumulates zombies**

Python only `wait()`s for PIDs it explicitly spawned, so an *adopted* orphan is never reaped:

```bash
unshare -Urpf --mount-proc python3 -c '
import subprocess, time
subprocess.run(["sh","-c","sleep 0.2 & exit 0"])   # grandchild orphaned -> reparented to PID 1
time.sleep(1)
print(subprocess.run(["ps","-eo","pid,ppid,stat,comm"],capture_output=True,text=True).stdout)
'
```

```
    PID    PPID STAT COMMAND
      1       0 S    python3
      3       1 Z    sleep      ← ZOMBIE: exited, but nobody called wait()
      4       1 R    ps
```

PID 3 is dead but its PID slot is still allocated. Anything in state `Z` is a leak.

> Enough of them and the namespace hits `pids.max` ([../4.cgroup/5.pids.md](../4.cgroup/5.pids.md)) and can no longer fork. **A container that mysteriously stops accepting work after a few days is almost always this.**

**Spot it in production:**

```bash
ps -eo stat,pid,ppid,comm | awk '$1 ~ /Z/'
ps aux | grep -c ' Z '
cat /proc/1/status | grep Threads
```

## **Why shells look fine (and why that fools people)**

```bash
unshare -Urpf --mount-proc bash -c '( sleep 0.2 & ); sleep 1; ps -eo pid,ppid,stat,comm'
```

```
    PID    PPID STAT COMMAND
      1       0 R    ps
```

No zombie at all. While a shell blocks in `wait()` for a foreground command it reaps **any** child, including adopted orphans.

> ⚠️ **Do not rely on this.** The moment your real PID 1 is a JVM, a Go binary, or nginx, the zombies come back. Testing your entrypoint with `bash` as PID 1 will hide the bug.

---

## **Fixes, in order of preference**

| # | Fix | How |
| - | --- | --- |
| 1 | **Make your app PID 1 and let it exit normally** | `exec myapp` in entrypoints; JSON-array `ENTRYPOINT` |
| 2 | **Use a real init as PID 1** | `tini`, `dumb-init`, `catatonit`, `s6-overlay` |
| 3 | **Let the platform do it** | `docker run --init` · Kubernetes `shareProcessNamespace: true` |

### Docker

```bash
docker run --init myimage        # injects tini as PID 1
```

```dockerfile
FROM alpine
RUN apk add --no-cache tini
ENTRYPOINT ["/sbin/tini", "--"]
CMD ["myapp"]
```

### Kubernetes

```yaml
spec:
  shareProcessNamespace: true    # the pause container becomes PID 1 for the whole pod
                                 # and reaps orphans from every container in it
```

> ⚠️ `shareProcessNamespace: true` also means **every container in the pod can see and signal the others' processes**, and `/proc` is shared. Great for debugging sidecars, a real consideration for isolation. Prefer fix #1 or #2 when you control the image.

## **What a correct init does — in ~10 lines**

That's the whole of `tini`:

```c
signal(SIGCHLD, ...);              /* wake on any child death   */
for (;;) {
    /* forward every signal we receive to the child process group */
    while (waitpid(-1, &status, WNOHANG) > 0)
        ;                          /* reap EVERY dead child, adopted or not */
    pause();
}
```

Two jobs: **reap everything**, and **forward signals** so `SIGTERM` reaches your app ([4.pid1-semantics.md](4.pid1-semantics.md)). Both of the classic PID-1 bugs, solved in one tiny binary.
