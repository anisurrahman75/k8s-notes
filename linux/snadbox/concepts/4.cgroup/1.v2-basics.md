# **1. cgroup v2 Basics — The Unified Hierarchy**

## **v1 vs v2 in one picture**

**v1** — one separate tree per controller, a process could sit at a different place in each. Unmanageable, and the reason v2 exists.

```
/sys/fs/cgroup/memory/mygroup/
/sys/fs/cgroup/cpu/some-other-group/
/sys/fs/cgroup/pids/yet-another/
```

**v2** — one tree. A cgroup is a directory; controllers are enabled *on* it.

```
/sys/fs/cgroup/                          ← root
├── init.scope
├── system.slice/
│   ├── sshd.service/
│   └── docker.service/
└── user.slice/
    └── user-1000.slice/
        └── user@1000.service/           ← your delegated subtree
            ├── app.slice/
            └── demo.slice/              ← yours to play with
```

```bash
stat -fc %T /sys/fs/cgroup      # cgroup2fs = v2
findmnt /sys/fs/cgroup
```

## **Where am I right now?**

```bash
cat /proc/self/cgroup
```

```
0::/user.slice/user-1000.slice/user@1000.service/session.slice/org.gnome.Shell@wayland.service
```

The format is `hierarchy-id:controllers:path`. In v2 there is exactly **one** hierarchy and it's always `0::`. The path is relative to `/sys/fs/cgroup`, so:

```bash
cat /sys/fs/cgroup$(cut -d: -f3 /proc/self/cgroup)/memory.current
```

**Every process is always in exactly one cgroup.** There is no "outside".

## **The core interface files**

Present in every cgroup:

| File | Purpose |
| ---- | ------- |
| `cgroup.procs` | **read:** PIDs in this cgroup · **write:** move a PID here |
| `cgroup.controllers` | which controllers are available *here* |
| `cgroup.subtree_control` | which controllers this cgroup enables *for its children* |
| `cgroup.events` | `populated 0/1` — has anyone in it? (pollable) |
| `cgroup.kill` | write `1` → SIGKILL every process in the subtree (kernel ≥ 5.14) |
| `cgroup.freeze` | write `1` → freeze the whole subtree |
| `cgroup.stat` | descendant counts |
| `cgroup.type` | `domain` / `threaded` |

```bash
CG=/sys/fs/cgroup/user.slice/user-$(id -u).slice/user@$(id -u).service/demo.slice
mkdir -p $CG
ls $CG
```

You did not create a single file — **the kernel populates the directory** the moment you `mkdir`. Which files appear depends on which controllers the parent enabled.

## **Rule 1: `subtree_control` — controllers flow downward**

A cgroup's `cgroup.controllers` (what it can use) is set by its **parent's** `cgroup.subtree_control` (what the parent hands down).

```bash
PARENT=/sys/fs/cgroup/user.slice/user-$(id -u).slice/user@$(id -u).service
cat $PARENT/cgroup.controllers      # what the parent HAS
cat $PARENT/cgroup.subtree_control  # what it PASSES DOWN
cat $PARENT/demo.slice/cgroup.controllers
```

```
cpu memory pids
cpu memory pids
cpu memory pids
```

**To enable a controller for children:**

```bash
echo "+memory +pids" > $CG/cgroup.subtree_control    # enable
echo "-memory"       > $CG/cgroup.subtree_control    # disable
```

> ⚠️ **You can only enable what your parent gave you:**
>
> ```bash
> echo "+io" > $CG/cgroup.subtree_control
> ```
>
> ```
> bash: echo: write error: No such file or directory
> ```
>
> `ENOENT` — the controller doesn't exist *here*, because the parent never delegated it. Not a permissions bug; it's the delegation model. See [2.rootless-delegation.md](2.rootless-delegation.md).

## **Rule 2: no internal processes**

> A cgroup may hold **processes** or have **children with controllers enabled** — not both.

```
❌  parent/  ← has processes
    └── child/  ← and controllers enabled

✅  parent/           ← no processes, subtree_control set
    ├── leaf-a/       ← processes here
    └── leaf-b/       ← and here
```

Violating it gives `EBUSY` when you write to `cgroup.subtree_control`. The reason is arbitration: the kernel would have to decide how to split CPU between "the processes sitting here" and "the child cgroups", and there's no sane answer.

**Consequence for you:** always put processes in **leaf** cgroups. This is exactly why systemd's tree is all `.slice` (intermediate) and `.scope`/`.service` (leaves).

---

## **Rule 3: limits are hierarchical and cumulative**

A child can never exceed an ancestor's limit, no matter what it writes to its own files.

```
user@1000.service   memory.max = max
└── demo.slice      memory.max = 100M      ← effective ceiling for everything below
    ├── a.scope     memory.max = 80M       ← gets 80M
    └── b.scope     memory.max = 500M      ← still capped at 100M by the parent
```

**Find the real limit on any cgroup by walking up:**

```bash
p=$(cut -d: -f3 /proc/self/cgroup)
while [ -n "$p" ]; do
  echo "$p -> $(cat /sys/fs/cgroup$p/memory.max 2>/dev/null)"
  p=${p%/*}
done
```

## **Moving processes in**

```bash
echo $$ > $CG/cgroup.procs          # move THIS shell
cat /proc/self/cgroup               # confirm
cat $CG/cgroup.procs                # who's in here
```

| Detail | |
| ------ | --- |
| One PID per write | write again for the next one |
| Children inherit | a process forked inside stays in the cgroup |
| Moving is instant | no restart needed |
| `cgroup.threads` | same idea at thread granularity |

> 💡 The standard trick is to move a **shell** into the cgroup, then everything you launch from it is automatically constrained — used in every demo in this folder.

## **Cleanup**

```bash
rmdir $CG          # only works if empty of processes AND child cgroups
```

```
rmdir: failed to remove '...': Device or resource busy
```

`EBUSY` means **either** live processes **or** leftover child cgroups. Check both:

```bash
cat $CG/cgroup.procs                 # who's inside
ls -d $CG/*/                         # any child cgroups?

echo 1 > $CG/cgroup.kill             # SIGKILL the whole subtree (kernel >= 5.14)
rmdir $CG/*/ 2>/dev/null             # children first — rmdir is not recursive
rmdir $CG
```

> `rmdir` on a cgroup is never recursive, and `rm -rf` does **not** work on cgroupfs. Delete leaves upward.

`cgroup.kill` is the clean modern way to tear down a container — one write, no PID list, no races.
