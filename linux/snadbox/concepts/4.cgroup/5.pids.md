---

## **The simplest controller, and the one that saves you**

| File | Meaning |
| ---- | ------- |
| `pids.max` | maximum processes/threads in this cgroup (`max` = unlimited) |
| `pids.current` | how many right now |
| `pids.peak` | high-water mark |
| `pids.events` | `max N` — how many times a fork was denied |

It counts **tasks**, so threads count too. A JVM with 200 threads needs `pids.max` ≥ 200 even though `ps` shows one process.

---

## **Demo: the limit bites**

```bash
echo 10 > $CG/pids.max

bash -c "echo \$\$ > $CG/cgroup.procs; for i in \$(seq 1 30); do sleep 5 & done; wait"
```

```
bash: fork: retry: Resource temporarily unavailable
bash: fork: retry: Resource temporarily unavailable
bash: fork: Interrupted system call
```

```bash
cat $CG/pids.events $CG/pids.peak
```

```
max 3
10
```

`fork()` returned `EAGAIN`. The shell got 10 tasks (itself + 9 sleeps) and every further fork was denied. Nothing crashed, nothing was killed — **new processes simply cannot be created.**

> 💡 That `EAGAIN` is the *whole* mechanism. It is why `pids.max` is the gentlest and most reliable of the limits: no OOM killer, no throttling, no surprises.

---

## **Why this is the anti-fork-bomb**

```bash
:(){ :|:& };:      # ⚠️ NEVER run this outside a pids-limited cgroup
```

Without `pids.max`, this exhausts the system-wide PID table in seconds and the machine becomes unloggable — you cannot even `fork` a shell to kill it.

Inside a cgroup with `pids.max`, the bomb hits its ceiling almost immediately and **the rest of the machine never notices**. Cleanup is one write:

```bash
echo 1 > $CG/cgroup.kill      # SIGKILL the entire subtree at once
cat $CG/pids.current
```

```
0
```

> ⚠️ **If you do try it:** a bash fork bomb *retries* forever, so the cgroup stays saturated until you kill it. Have the `cgroup.kill` command ready in another terminal first. The `seq`-based demo above shows the same `EAGAIN` behaviour with no cleanup drama.

## **Picking a value**

| Workload | Reasonable `pids.max` |
| -------- | --------------------- |
| Single-process CLI tool | 32 |
| Web server + workers | 256–1024 |
| JVM / Go service (threads count!) | 512–4096 |
| CI runner / build container | 4096+ |
| Kubernetes default | `podPidsLimit`, often 4096 |

**Measure instead of guessing:**

```bash
cat $CG/pids.peak            # what it actually used
```

Then set `pids.max` to roughly 2× the observed peak.

## **Where it shows up**

```bash
# Docker
docker run --pids-limit 100 myimage

# systemd
systemd-run --user --scope -p TasksMax=100 -- bash

# Kubernetes — node-level, in the kubelet config
```

```yaml
podPidsLimit: 4096          # per pod
```

```bash
# on a node
cat /sys/fs/cgroup/kubepods.slice/.../pids.max
cat /proc/sys/kernel/pid_max        # system-wide ceiling, usually 4194304
```

## **Debugging PID exhaustion**

Symptoms: `fork: Resource temporarily unavailable`, `Cannot allocate memory` on `posix_spawn`, "too many open processes".

```bash
cat $CG/pids.current $CG/pids.max     # am I at the ceiling?
cat $CG/pids.events                   # has it been denied before?

# who is eating them?
ps -eLf | wc -l                                     # total tasks including threads
ps -eo pid,nlwp,comm --sort=-nlwp | head            # top thread users
ps -eo stat,pid,comm | awk '$1 ~ /Z/' | wc -l       # zombies
```

> 🔑 **A slowly climbing `pids.current` that never comes down is almost always leaked zombies** — a PID 1 that doesn't reap. See [../2.pid/5.reaping.md](../2.pid/5.reaping.md). The `pids` controller turns that leak from "the node falls over at 3 a.m." into "one container stops forking".
