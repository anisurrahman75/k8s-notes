# **6. `chroot` vs `pivot_root`**

← [5.rootfs.md](5.rootfs.md) | back to [README](README.md)

---

## **The difference in one table**

| | `chroot(2)` | `pivot_root(2)` |
| --- | --- | --- |
| What it changes | the **process's** idea of `/` | the **mount namespace's** root |
| Old root afterwards | still mounted, still reachable via other fds/mounts | detachable — `umount` it and it's *gone* |
| Escapable | **yes**, famously — a few lines of C with any open dir fd | no |
| Needs a mount namespace | no | effectively yes |
| Used by | build tools, rescue shells | **every container runtime** |

> `chroot` is a *convenience*, never a security boundary. `pivot_root` inside a mount namespace is the real thing.

---

## **Why `chroot` is escapable**

The classic escape, in essence:

```c
mkdir("subdir", 0755);
int fd = open(".", O_RDONLY);   /* fd to the CURRENT root, before chrooting */
chroot("subdir");               /* now cwd is OUTSIDE the new root          */
fchdir(fd);                     /* jump back out through the saved fd       */
for (int i = 0; i < 1024; i++) chdir("..");   /* walk up to the real /      */
chroot(".");                    /* make the real root our root again        */
execl("/bin/sh", "sh", NULL);
```

`chroot` never checks whether your cwd or your open file descriptors are inside the new root. Any process with `CAP_SYS_CHROOT` — including your fake root in a user namespace — can walk straight back out.

`pivot_root` has no equivalent hole: it moves the *mount* itself, so there is no outside left in the namespace to walk back to.

## **Demo: `chroot` vs the full thing**

**chroot alone** — the filesystem view changes:

```bash
ROOTFS=/tmp/nslab/rootfs
unshare -Ur chroot $ROOTFS /bin/busybox sh -c 'export PATH=/bin; echo "root: $(ls /)"'
```

```
root: bin dev etc oldroot proc sys tmp
```

(busybox `ls` prints one entry per line when not on a tty — collapsed here for readability.)

Looks like a container. But the mount table underneath is still the host's, and the host root is one `fchdir` away.

**`pivot_root` in a mount + PID namespace** — the real sandbox:

```bash
ROOTFS=/tmp/nslab/rootfs

unshare -Urmpf bash -c "
  mount --bind $ROOTFS $ROOTFS       # pivot_root requires new_root to be a mount point
  cd $ROOTFS
  pivot_root . oldroot               # old root moves to \$ROOTFS/oldroot
  exec /bin/busybox sh -c '
    export PATH=/bin
    mount -t proc proc /proc         # our own procfs
    umount -l /oldroot               # detach the host tree entirely
    rmdir /oldroot

    echo \"root:   \$(ls /)\"
    echo \"mounts: \$(wc -l < /proc/mounts)\"
    cat /proc/mounts
    echo \"pid:    \$\$\"
  '
"
```

```
root:   bin dev etc proc sys tmp
mounts: 2
/dev/mapper/ubuntu--vg-ubuntu--lv / ext4 rw,relatime 0 0
proc /proc proc rw,relatime 0 0
pid:    1
```

**Two mounts. That's the entire universe this process can reach.** No `/home`, no `/etc/shadow`, no snap loops, no host `/proc`. Compare with the host's 68 mounts.

## **The five steps, and why each is needed**

```bash
1.  unshare -m                          # own mount table — everything below is invisible outside
2.  mount --bind $ROOTFS $ROOTFS        # pivot_root REQUIRES new_root to be a mount point
3.  cd $ROOTFS && pivot_root . oldroot  # swap: rootfs becomes /, old / becomes /oldroot
4.  mount -t proc proc /proc            # the new root has an empty /proc
5.  umount -l /oldroot                  # cut the last link to the host
```

### Requirements `pivot_root(2)` enforces

| Requirement | Symptom if violated |
| ----------- | ------------------- |
| `new_root` must be a **mount point** | `pivot_root: failed to change root from '.' to 'oldroot': Invalid argument` |
| `put_old` must be **under** `new_root` | `pivot_root: Invalid argument` |
| Neither may be the current root | `Invalid argument` |
| The current root must not be `shared` | `pivot_root: Device or resource busy` → `mount --make-rprivate /` first |

> **Step 2 is the one everybody forgets.** `pivot_root . oldroot` fails with a bafflingly generic `Invalid argument` if `$ROOTFS` is a plain directory. Bind it to itself and it becomes a mount point.

### Why `umount -l` (lazy)?

At the moment you call it, your shell's cwd and open fds may still reference `/oldroot`. A plain `umount` returns `EBUSY`. Lazy unmount detaches it from the tree immediately and frees it when the last reference goes — which is exactly what you want here.

---

## **The `exec` in step 3.5**

```bash
pivot_root . oldroot
exec /bin/busybox sh -c '...'
```

Why `exec` into a busybox shell instead of continuing in `bash`?

Your `bash` came from the **host**, dynamically linked against host libraries that no longer exist after the pivot:

```
bash: line 5: /usr/bin/mount: No such file or directory
bash: line 6: umount: command not found
bash: line 8: ls: command not found
```

The running `bash` survives (its pages are already mapped), but it cannot `exec` anything. `exec`ing the **static** busybox from inside the new root fixes it permanently. This is the same failure mode as [5.rootfs.md's missing-loader trap](5.rootfs.md#dynamic-binaries-need-their-libraries) — and why container images bundle their own libc.

## **What real runtimes do**

`runc`'s sequence, essentially:

```bash
mount --make-rslave /                   # never leak mounts back to the host
mount -t overlay overlay -o lowerdir=...,upperdir=...,workdir=... /rootfs
mount --bind /rootfs /rootfs
# ... bind volumes, /etc/hosts, /etc/resolv.conf, minimal /dev ...
cd /rootfs && pivot_root . .oldroot
mount -t proc proc /proc
mount -t sysfs sys /sys
umount -l /.oldroot && rmdir /.oldroot
mount -o remount,ro /                   # if readOnlyRootFilesystem
exec /the/entrypoint
```

Every line maps to something in this folder: `--make-rslave` → [2.propagation.md](2.propagation.md), overlay → [4.overlayfs.md](4.overlayfs.md), binds → [3.bind-mounts.md](3.bind-mounts.md), rootfs → [5.rootfs.md](5.rootfs.md).

> Some runtimes use `MS_MOVE` + `chroot` instead of `pivot_root` (required inside an existing container where `pivot_root` may be refused). Equivalent effect; `pivot_root` is preferred wherever it works.

## **Quick reference**

```bash
# --- create ---
unshare -Urm bash                              # own mount table
unshare -Urm --propagation unchanged bash      # keep inherited propagation (= slave)
unshare -Urmpf --mount-proc bash               # mount + pid, ready for pivot_root

# --- inspect ---
findmnt                                        # tree view
findmnt -o TARGET,PROPAGATION                  # propagation state
findmnt -no OPTIONS --target /path             # is it really ro?
cat /proc/self/mountinfo                       # authoritative raw view
mountpoint /path                               # is this a mount point?

# --- build ---
mount -t tmpfs -o size=64M tmpfs /path
mount --bind  /src /dst                        # leaf directory
mount --rbind /src /dst                        # anything with submounts
mount -o remount,bind,ro /src /dst             # make it read-only (verify!)
mount --make-rslave /                          # standard container setup
mount -t overlay overlay -o lowerdir=L,upperdir=U,workdir=W merged

# --- pivot ---
mount --bind $ROOTFS $ROOTFS
cd $ROOTFS && pivot_root . oldroot
exec /bin/busybox sh                           # static shell from the NEW root
mount -t proc proc /proc && umount -l /oldroot

# --- rules ---
#  pivot_root's new_root MUST be a mount point   -> bind it to itself
#  put_old MUST be under new_root
#  umount the old root LAZILY (-l)
#  exec a STATIC binary from the new root
#  in a userns you cannot unmount inherited mounts -> pivot, don't dismantle
```
