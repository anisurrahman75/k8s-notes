# **2. The User Namespace — Why You Don't Need Root**

## **The Enabler**

Creating any namespace type normally requires `CAP_SYS_ADMIN`. The user namespace is the exception, and it bootstraps everything else:

> When you create a **user namespace**, the kernel grants you **a full capability set inside it** — and those capabilities are enough to create every other namespace type nested within it.

That is why `unshare -U` makes this entire folder work without `sudo`. `-r` is shorthand for "and map me to root inside it".

---

## **Demo: become root without being root**

```bash
unshare -Ur bash -c 'cat /proc/self/uid_map; id'
```

```
         0       1000          1
uid=0(root) gid=0(root) groups=0(root),65534(nogroup)
```

### Reading `uid_map`

Three columns:

```
 inside-uid   outside-uid   count
     0           1000         1
```

→ *"UID 0 **inside** this namespace maps to UID 1000 **outside**."*

You are `root` in the namespace. You are still `anisur` to the rest of the kernel. `gid_map` works identically.

`count` is a range length. A real container runtime writes something like:

```
 0    100000    65536
```

→ *"inside UIDs 0–65535 map to host UIDs 100000–165535."* This is what `/etc/subuid` and `/etc/subgid` allocate, and what lets rootless Podman run a container whose files are owned by many different UIDs without any of them being real host users.

```bash
cat /etc/subuid /etc/subgid      # your allocated ranges
```

## **Demo: prove the root is fake**

```bash
unshare -Ur bash -c 'id; touch /etc/definitely-not-allowed'
```

```
uid=0(root) gid=0(root) groups=0(root),65534(nogroup)
touch: cannot touch '/etc/definitely-not-allowed': Permission denied
```

**Why:** your fake root holds `CAP_DAC_OVERRIDE` **inside** the namespace. But `/etc` is owned by the **real** UID 0, which is *unmapped* in your namespace — so the kernel treats you as `nobody` for that file and the capability does not apply.

This is precisely the security model of rootless containers (Podman, rootless Docker, unprivileged LXC): full power over your own mapped range, zero power outside it.

**The `65534(nogroup)` in your groups list is the same idea** — any host GID you are not mapped to shows up as the overflow ID:

```bash
unshare -Ur ls -l /etc/shadow
```

```
-rw-r----- 1 nobody nogroup 1432 May 26 14:33 /etc/shadow
```

`root:shadow` outside, `nobody:nogroup` inside — because neither is in your map.

## **What your fake root CAN do**

Inside the namespace, against resources the namespace owns:

```bash
unshare -Urm bash -c 'mkdir -p /tmp/t && mount -t tmpfs tmpfs /tmp/t && df -h /tmp/t | tail -1'
```

```
tmpfs            16G     0   16G   0% /tmp/t
```

Mounting a filesystem — normally strictly root-only — works, because the mount namespace is *owned by* your user namespace. That ownership link is the whole mechanism. See [4.lifetime-and-nesting.md](4.lifetime-and-nesting.md#ownership).

---

## **What it still cannot do**

| Blocked                         | Why                                                   |
| ------------------------------- | ----------------------------------------------------- |
| Write files owned by unmapped UIDs | Capabilities don't apply outside your map          |
| Load kernel modules             | `CAP_SYS_MODULE` is meaningless outside the init userns |
| Mount most block-backed filesystems (`ext4`, `xfs`) | Untrusted on-disk metadata → kernel attack surface |
| Change host sysctls             | `/proc/sys` is owned by the init userns               |
| Bind ports < 1024 on the host   | Only in an owned network namespace, not the host's    |

Allowed filesystem types in a user namespace are essentially: `tmpfs`, `proc`, `sysfs`, `devpts`, `ramfs`, `mqueue`, `cgroup2`, `overlay` (5.11+), `fuse` (4.18+), plus bind mounts. That list is exactly why rootless container images use **overlayfs or fuse-overlayfs** and never a loopback ext4.

## **Checking a process's user namespace**

```bash
unshare -Ur --fork sleep 60 &
sleep 1; PID=$(pgrep -x sleep | tail -1)

readlink /proc/$PID/ns/user       # which userns
cat /proc/$PID/uid_map            # its mapping
lsns -t user -p $PID
```

> ⚠️ **`uid_map` is write-once.** Once written it can never change, and it must be written by a process in the *parent* namespace before the child can use its capabilities meaningfully. `unshare -r` does this for you. If you ever see `nobody` everywhere inside a container, an unwritten or mismatched `uid_map` is the first thing to check.
