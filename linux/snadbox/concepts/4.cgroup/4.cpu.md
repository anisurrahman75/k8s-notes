## **Two completely different mechanisms**

| | `cpu.max` | `cpu.weight` |
| --- | --- | --- |
| Type | **hard ceiling** (bandwidth) | **relative share** |
| Enforced | always, even on an idle machine | only under contention |
| Idle CPU available? | ❌ still throttled | ✅ take it all |
| Kubernetes | `limits.cpu` | `requests.cpu` |
| Default | `max 100000` (unlimited) | `100` (range 1–10000) |

Understanding that `cpu.max` throttles **even when the machine is completely idle** is the single most important thing on this page.

---

## **`cpu.max` — hard bandwidth limit**

Format: `QUOTA PERIOD`, both in microseconds.

```
QUOTA / PERIOD  =  how many CPUs this cgroup may use
```

| Setting | Meaning |
| ------- | ------- |
| `20000 100000` | 20 ms of CPU per 100 ms = **0.2 CPU** |
| `100000 100000` | **1.0 CPU** |
| `200000 100000` | **2.0 CPUs** (across any number of threads) |
| `max 100000` | unlimited |

### Demo: 20% of one core

```bash
echo "20000 100000" > $CG/cpu.max

bash -c "echo \$\$ > $CG/cgroup.procs; time (timeout 3 bash -c 'while :; do :; done')"
```

```
real	0m3.033s
user	0m0.610s
sys	0m0.002s
```

**3.03 s wall, 0.61 s CPU → 20%.** Exactly the quota. The loop wanted a whole core and got one fifth of one.

### The throttling receipt

```bash
head -8 $CG/cpu.stat
```

```
usage_usec 657077
user_usec 622494
system_usec 34583
nice_usec 0
core_sched.force_idle_usec 0
nr_periods 31
nr_throttled 31
throttled_usec 2419597
```

| Field | Meaning |
| ----- | ------- |
| `nr_periods 31` | 31 × 100 ms periods elapsed |
| `nr_throttled 31` | it was throttled in **every single one** |
| `throttled_usec 2419597` | **2.42 seconds spent frozen**, doing nothing |

> 🔑 **`nr_throttled / nr_periods` is the metric to alert on.** A ratio near 1.0 means the workload is CPU-starved by its own limit. This is the number behind "my pod is slow but CPU usage looks low" — it *is* low, because it's sitting in the throttled state.

### Demo: 2 CPUs shared by 4 threads

```bash
echo "200000 100000" > $CG/cpu.max
bash -c "echo \$\$ > $CG/cgroup.procs; for i in 1 2 3 4; do timeout 3 bash -c 'while :; do :; done' & done; wait"
head -3 $CG/cpu.stat
```

```
usage_usec 6717655        ← ~6.7 CPU-seconds over 3 s wall = 2.2 CPUs
```

Four busy loops on a 16-core machine consumed **2 cores' worth**, not four. The quota is a budget for the whole cgroup, not per process.

## **`cpu.weight` — proportional share**

```bash
cat $CG/cpu.weight
```

```
100
```

Range 1–10000, default 100. Weight only matters **when CPUs are contended**:

```
demo-a  weight 100   ─┐
                      ├─ contended → a gets 1/3, b gets 2/3
demo-b  weight 200   ─┘

                       idle machine → whoever is running takes everything
```

```bash
mkdir -p $CG/a $CG/b
echo "+cpu" > $CG/cgroup.subtree_control
echo 100 > $CG/a/cpu.weight
echo 200 > $CG/b/cpu.weight
```

> `cpu.weight.nice` is the same knob expressed on the −20…+19 nice scale, for convenience.

**Why Kubernetes maps `requests.cpu` to weight:** requests are a *guarantee under contention*, not a cap. A pod requesting 100m can happily use 8 cores on an idle node — until neighbours want CPU, at which point the weights arbitrate.

## **The `cpu.max` trap in Kubernetes**

```yaml
resources:
  requests: { cpu: "100m" }    # -> cpu.weight  ≈ 4
  limits:   { cpu: "500m" }    # -> cpu.max = "50000 100000"
```

A multi-threaded runtime (JVM, Go, Node with a worker pool) sees `nproc` = **16** and starts 16 threads. Those 16 threads burn the 50 ms quota in ~3 ms, then the entire process is **frozen for the remaining 97 ms** of every period. Latency goes through the roof while average CPU usage looks like a comfortable 30%.

**Fixes:**

| Fix | How |
| --- | --- |
| Tell the runtime the truth | `GOMAXPROCS` (`automaxprocs`), `-XX:ActiveProcessorCount`, `UV_THREADPOOL_SIZE` |
| Raise the limit | or remove it, keeping requests for fairness |
| Shorten the period | `cpu.max` period 10000 → smoother, more overhead |
| Check before blaming the app | `nr_throttled/nr_periods` on the pod's cgroup |

```bash
# on a node — is this pod actually throttled?
PID=$(sudo crictl inspect <id> | jq .info.pid)
CG=/sys/fs/cgroup$(sudo cat /proc/$PID/cgroup | cut -d: -f3)
cat $CG/cpu.max $CG/cpu.stat
```

## **PSI — the honest CPU metric**

```bash
cat $CG/cpu.pressure
```

```
some avg10=0.00 avg60=0.00 avg300=0.00 total=2217531
full avg10=0.00 avg60=0.00 avg300=0.00 total=2217159
```

`some avg10` = % of the last 10 s during which at least one task was **runnable but waiting for CPU**. Unlike load average it is per-cgroup and normalized, so it means the same thing on a 4-core and a 96-core box.

| Metric | Tells you |
| ------ | --------- |
| `usage_usec` | how much CPU you got |
| `nr_throttled` | how often your **own limit** stopped you |
| `cpu.pressure` | how much you're waiting on **other people's** work |
