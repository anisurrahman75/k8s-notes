# **5. What Namespaces Do NOT Isolate**

← [4.lifetime-and-nesting.md](4.lifetime-and-nesting.md) | back to [README](README.md)

---

The most important page in this folder for security thinking.

> **Namespaces isolate *visibility*. They do not isolate *consumption*, and they do not isolate *the kernel*.**

| Not isolated by namespaces | Consequence                                    | Real fix                                     |
| -------------------------- | ---------------------------------------------- | -------------------------------------------- |
| CPU, RAM, PIDs, IO         | A namespaced process can starve the whole host | **cgroups** → [../4.cgroup/](../4.cgroup/)   |
| The kernel itself          | One kernel LPE bug = full host compromise      | seccomp, gVisor, Kata / Firecracker microVMs |
| Syscall surface            | ~350 syscalls still reachable from the sandbox | **seccomp-bpf** filters                      |
| `/proc/sys`, `/sys` writes | Kernel tunables are global                     | mount `ro`, drop `CAP_SYS_ADMIN`             |
| Device nodes               | `/dev/sda` in the rootfs = raw disk access     | device cgroup / minimal `/dev`               |
| Kernel keyring, wall clock | Shared unless separately namespaced            | keyring ns, time ns                          |

---

## **Demo: full isolation, zero resource protection**

Fully namespaced — own PID space, own `/proc`, own hostname — and it still eats a whole CPU of the host:

```bash
unshare -Urpf --mount-proc bash -c 'timeout 5 bash -c "while :; do :; done"' &
sleep 1
top -bn1 | head -12
uptime
```

You will see load average climb on the **host**. The sandbox has no idea it is doing anything wrong, and nothing stops it.

Same story for memory:

```bash
# careful — this is the failure mode, not a recommendation
unshare -Urpf --mount-proc python3 -c 'b=bytearray(); [b.extend(bytearray(1024*1024)) for _ in range(2000)]'
```

Without a cgroup, that allocates 2 GB of **host** RAM and can trigger the **host's** OOM killer, which may pick an innocent host process as its victim.

> 🔑 **This is exactly why the [combined demo](../../demo/README.md) uses namespaces *and* cgroups.** Namespaces alone give you a sandbox that can politely not-see the host while comfortably destroying it.

## **Demo: the kernel is shared**

```bash
uname -r
unshare -Urpf --mount-proc uname -r
```

```
6.17.0-40-generic
6.17.0-40-generic
```

Same kernel. Same code, same bugs, same syscall table. A container escape is usually not "a namespace was misconfigured" — it is "a kernel bug was reachable from inside".

**Mitigation is seccomp, not namespaces.** Docker's default profile blocks ~44 syscalls, including nested namespace creation:

```bash
docker run --rm alpine sh -c 'unshare -Ur echo nested'
```

```
unshare: unshare(0x10000000): Operation not permitted
```

`0x10000000` is `CLONE_NEWUSER` — the syscall never reached the namespace code, seccomp rejected it first. That is a *different* layer doing the work.

## **The layered model**

No single mechanism makes a sandbox. Real isolation stacks them:

```
┌────────────────────────────────────────────────┐
│ VM / microVM (Kata, Firecracker)  ← own kernel │
│ ┌────────────────────────────────────────────┐ │
│ │ seccomp-bpf        ← which syscalls        │ │
│ │ capabilities       ← which privileged ops  │ │
│ │ LSM (AppArmor/SELinux) ← which objects     │ │
│ │ cgroups            ← how much              │ │
│ │ namespaces         ← what is visible       │ │
│ │ ┌────────────────────────────────────────┐ │ │
│ │ │            your process                │ │ │
│ │ └────────────────────────────────────────┘ │ │
│ └────────────────────────────────────────────┘ │
└────────────────────────────────────────────────┘
```

**Namespaces are the bottom layer, not the whole stack.** This folder covers namespaces and cgroups — the two you can fully explore rootless on your own laptop. seccomp, capabilities and LSMs are the natural next step.

---

## **Checklist for a real sandbox**

| Layer | Minimum |
| ----- | ------- |
| Namespaces | `user`, `pid`, `mount`, `uts`, `ipc`, `net` |
| cgroup | `memory.max`, `pids.max`, `cpu.max`, `io.max` |
| Rootfs | read-only where possible, no host bind-mounts, minimal `/dev` |
| Capabilities | drop all, add back only what's needed |
| seccomp | default-deny profile |
| No | `--privileged`, `hostPID`, `hostNetwork`, `/var/run/docker.sock` |
