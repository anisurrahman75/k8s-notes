## **The problem**

`/sys/fs/cgroup` is owned by root. A normal user can't `mkdir` there:

```bash
mkdir /sys/fs/cgroup/mygroup
```

```
mkdir: cannot create directory '/sys/fs/cgroup/mygroup': Permission denied
```

Unlike namespaces, **a user namespace does not grant you cgroup authority** — cgroupfs permissions are plain filesystem permissions, and your fake root is unmapped there.

## **The solution: systemd delegation**

systemd creates a per-user subtree, **chowns it to you**, and hands down a subset of controllers:

```bash
U=$(id -u)
ROOT=/sys/fs/cgroup/user.slice/user-$U.slice/user@$U.service

ls -ld $ROOT
cat $ROOT/cgroup.controllers
```

```
drwxr-xr-x 6 anisur anisur 0 Aug 11 ... /sys/fs/cgroup/user.slice/user-1000.slice/user@1000.service
cpu memory pids
```

Owned by you. `cpu`, `memory`, `pids` delegated. That's everything the demos in this folder need.

```bash
CG=$ROOT/demo.slice
mkdir -p $CG && echo "created $CG"
echo 100M > $CG/memory.max && cat $CG/memory.max
```

```
created /sys/fs/cgroup/user.slice/user-1000.slice/user@1000.service/demo.slice
104857600
```

> 💡 **Set this once per shell** — every page that follows uses `$CG`:
>
> ```bash
> U=$(id -u)
> CG=/sys/fs/cgroup/user.slice/user-$U.slice/user@$U.service/demo.slice
> mkdir -p $CG
> ```

## **What is NOT delegated, and why**

```bash
cat /sys/fs/cgroup/cgroup.controllers      # what the kernel has
cat $ROOT/cgroup.controllers               # what you got
```

```
cpuset cpu io memory hugetlb pids rdma misc dmem
cpu memory pids
```

| Missing | Why |
| ------- | --- |
| `io` | needs block-device knowledge; a user could starve system IO |
| `cpuset` | pinning to CPUs is a machine-wide scheduling decision |
| `hugetlb`, `rdma`, `misc` | scarce global resources |

**Widen it if you need to** (root, persistent):

```bash
sudo mkdir -p /etc/systemd/system/user@.service.d
sudo tee /etc/systemd/system/user@.service.d/delegate.conf <<'EOF'
[Service]
Delegate=cpu cpuset io memory pids
EOF
sudo systemctl daemon-reload
# log out and back in
```

This is exactly what the **rootless Podman / rootless Docker** setup docs tell you to do.

## **Two ways to get a cgroup**

### A. By hand — full control, what you'll use for learning

```bash
mkdir -p $CG
echo 50M > $CG/memory.max
echo $$  > $CG/cgroup.procs      # this shell, and everything it spawns
```

Everything is explicit and visible. Downside: **you** must clean up.

### B. Via `systemd-run` — managed, self-cleaning

```bash
systemd-run --user --scope -p MemoryMax=50M -p CPUQuota=20% -- bash
```

systemd creates a transient `.scope`, applies the limits, and **removes the cgroup when the process exits**. Nothing to clean up.

```bash
# where did it put me, and did the limit land?
systemd-run --user --scope -q -p MemoryMax=50M -- bash -c \
  'CG=/sys/fs/cgroup$(cut -d: -f3 /proc/self/cgroup); echo "$CG"; cat $CG/memory.max'
```

```
/sys/fs/cgroup/user.slice/user-1000.slice/user@1000.service/app.slice/run-rf322f95f53a54ce38e71063b2a379182.scope
52428800
```

Same kernel files, same enforcement — systemd is only a bookkeeper. Details in [7.systemd-and-k8s.md](7.systemd-and-k8s.md).

| | By hand | `systemd-run` |
| --- | --- | --- |
| Understand what's happening | ✅ everything explicit | ❌ hidden |
| Cleanup | ❌ manual | ✅ automatic |
| Survives your shell dying | ✅ (leaks) | ❌ (cleaned) |
| Good for | learning, scripts, [the demo](../../demo/README.md) | day-to-day use |

## **The delegation rules (kernel's view)**

For a subtree to be safely delegated to an unprivileged user, they must own:

| Path | Why |
| ---- | --- |
| the cgroup **directory** | to `mkdir` children |
| `cgroup.procs` | to move processes in |
| `cgroup.subtree_control` | to enable controllers for children |
| `cgroup.threads` | for thread-granularity moves |

Notably **not** the resource-limit files of the delegation root itself — you cannot raise your own ceiling, only subdivide what you were given ([Rule 3](1.v2-basics.md#rule-3-limits-are-hierarchical-and-cumulative)).

```bash
ls -l $ROOT/cgroup.procs $ROOT/cgroup.subtree_control $ROOT/memory.max
```

```
-rw-r--r-- 1 anisur anisur 0 ... cgroup.procs
-rw-r--r-- 1 anisur anisur 0 ... cgroup.subtree_control
-rw-r--r-- 1 root   root   0 ... memory.max        ← root owns the ceiling
```

The kernel also enforces `nsdelegate` (visible in the mount options), which prevents processes from being migrated *across* cgroup-namespace boundaries:

```bash
findmnt -no OPTIONS /sys/fs/cgroup
```

```
rw,nosuid,nodev,noexec,relatime,nsdelegate,memory_recursiveprot
```

## **Cleanup helper**

Worth keeping in your shell rc while working through this folder:

```bash
cgclean() {
  local CG=/sys/fs/cgroup/user.slice/user-$(id -u).slice/user@$(id -u).service/demo.slice
  [ -d "$CG" ] || return 0
  echo 1 > "$CG/cgroup.kill" 2>/dev/null
  rmdir "$CG"/*/ 2>/dev/null
  rmdir "$CG"  2>/dev/null && echo "cleaned $CG"
}
```
