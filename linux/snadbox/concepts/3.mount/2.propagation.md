# **2. Mount Propagation — shared / private / slave**

## **The surprise**

A new mount namespace does **not** give you a disconnected table. It gives you a *copy* that may still be **wired to the original**. Whether new mounts flow between them is controlled per-mount by its **propagation type**.

| Type            | New mounts flow **in** (parent → me) | New mounts flow **out** (me → parent) |
| --------------- | ------------------------------------ | ------------------------------------- |
| **shared**      | ✅ yes                                | ✅ yes                                 |
| **slave**       | ✅ yes                                | ❌ no                                  |
| **private**     | ❌ no                                 | ❌ no                                  |
| **unbindable**  | ❌ no — and cannot be bind-mounted at all           |

Mounts that propagate to each other form a **peer group** (`shared:13` in `mountinfo`).

---

## **Your host is almost certainly `shared`**

systemd sets `/` to `shared` at boot, precisely so that plugging in a USB stick becomes visible to services in other mount namespaces.

```bash
findmnt -no TARGET,PROPAGATION /
findmnt -o TARGET,PROPAGATION | head -5
```

```
/      shared
TARGET                     PROPAGATION
/                          shared
├─/sys                     shared
│ ├─/sys/kernel/security   shared
│ ├─/sys/fs/cgroup         shared
```

## **Demo: private vs slave, side by side**

This is the demo that makes propagation click. Two sandboxes wait; the host mounts a tmpfs; only one of them notices.

```bash
S=/tmp/nslab; mkdir -p $S/prop

# sandbox A — inherits propagation (ends up SLAVE inside a user namespace)
unshare -Urm --propagation unchanged bash -c \
  "sleep 5; echo -n 'SLAVE ns sees:   '; findmnt -no FSTYPE,TARGET --target $S/prop" &

# sandbox B — unshare's default: PRIVATE
unshare -Urm bash -c \
  "sleep 5; echo -n 'PRIVATE ns sees: '; findmnt -no FSTYPE,TARGET --target $S/prop" &

sleep 1
sudo mount -t tmpfs tmpfs $S/prop && echo ">>> host mounted tmpfs on $S/prop"
sleep 6
sudo umount $S/prop
```

```
>>> host mounted tmpfs on /tmp/nslab/prop
PRIVATE ns sees: ext4   /                    ← blind: still the underlying ext4 root
SLAVE ns sees:   tmpfs  /tmp/nslab/prop      ← saw the host's new mount appear
```

Same host event, two different realities — decided entirely by propagation type.

## **What `unshare` does by default**

```bash
unshare -Urm bash -c 'findmnt -no PROPAGATION /'
```

```
private
```

`unshare -m` **recursively makes everything private**, which is why most simple demos "just work" in isolation. Ask for the raw inherited state and you get something different:

```bash
unshare -Urm --propagation unchanged bash -c 'findmnt -no PROPAGATION /'
```

```
private,slave
```

> 🔑 **A user namespace forces at least `slave`.** The kernel will never let an unprivileged mount namespace propagate mounts *out* to its parent — that would let any user mount things onto the host. Mounts can flow **in**, never **out**.

`--propagation` accepts: `private` (default) · `shared` · `slave` · `unchanged`.

## **Changing propagation by hand**

```bash
mount --make-private   /some/mount
mount --make-shared    /some/mount
mount --make-slave     /some/mount
mount --make-unbindable /some/mount

# recursive variants — what you actually want on a tree
mount --make-rprivate /
mount --make-rslave   /
mount --make-rshared  /
```

**Every container runtime does this as step one:**

```bash
mount --make-rslave /      # see the host's new mounts; never leak ours back
```

`runc` runs the equivalent of `--make-rslave` (or `rprivate`, per config) on the whole tree before building the container's rootfs. Without it, the container's `pivot_root` and its `/proc` mount would propagate straight back into the host's table.

## **Where this bites in production**

| Symptom | Cause | Fix |
| ------- | ----- | --- |
| Docker `-v /mnt/nfs:/data`: mounts added on the host later don't appear in the container | bind mount is `private` | `-v /mnt/nfs:/data:rslave` |
| Kubernetes CSI driver's mounts invisible to pods | propagation not set | `mountPropagation: HostToContainer` (= rslave) |
| A CSI node plugin's mounts must reach the host | needs to propagate out | `mountPropagation: Bidirectional` (= rshared, **privileged only**) |
| Host `/` accumulates thousands of stale container mounts | mounts leaked out via `shared` | `--make-rslave` before building the rootfs |

```yaml
volumeMounts:
  - name: host-data
    mountPath: /data
    mountPropagation: HostToContainer    # None (default) | HostToContainer | Bidirectional
```

| Kubernetes value    | Linux equivalent |
| ------------------- | ---------------- |
| `None` (default)    | `rprivate`       |
| `HostToContainer`   | `rslave`         |
| `Bidirectional`     | `rshared` — requires a privileged container |

> ⚠️ `Bidirectional` lets a pod create mounts **on the node**. Only CSI drivers and similar infrastructure should ever have it.

## **Reading propagation state**

```bash
findmnt -o TARGET,PROPAGATION                 # human
findmnt -no PROPAGATION --target /some/path   # one path
grep -E 'shared|master|propagate' /proc/self/mountinfo | head
```

In `mountinfo`, the optional fields tell you everything:

| Field | Meaning |
| ----- | ------- |
| `shared:13` | member of peer group 13 — propagates both ways |
| `master:13` | **slave** of peer group 13 — receives only |
| `shared:14 master:13` | shared with 14, slave of 13 (both at once) |
| *(nothing)* | private |
| `unbindable` | cannot be bind-mounted |
