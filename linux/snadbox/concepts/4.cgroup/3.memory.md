# **3. The `memory` Controller**

U=$(id -u); CG=/sys/fs/cgroup/user.slice/user-$U.slice/user@$U.service/demo.slice
mkdir -p $CG

---

## **The knobs**

| File | Meaning |
| ---- | ------- |
| `memory.max` | **hard limit** — exceed it and the OOM killer fires |
| `memory.high` | **soft limit** — the kernel throttles and reclaims aggressively, but never kills |
| `memory.low` | best-effort protection *from* reclaim |
| `memory.min` | hard protection from reclaim (guaranteed) |
| `memory.current` | how much is charged right now |
| `memory.peak` | high-water mark |
| `memory.swap.max` | swap ceiling — set to `0` to make limits deterministic |
| `memory.events` | counters: `max`, `oom`, `oom_kill` |
| `memory.stat` | detailed breakdown (anon, file, slab, …) |
| `memory.oom.group` | `1` = kill the **whole** cgroup together, not one victim |

Values are bytes; `K`/`M`/`G` suffixes accepted on write, always read back as bytes. `max` means unlimited.

---

## **Demo: a real OOM kill**

```bash
echo 50M > $CG/memory.max
echo 0   > $CG/memory.swap.max        # otherwise it swaps instead of dying

bash -c "echo \$\$ > $CG/cgroup.procs; python3 -c '
b = bytearray()
for i in range(200):
    b += bytearray(1024*1024)         # +1 MiB each loop
    print(i, flush=True)
'" | tail -3
```

```
42
43
Killed
```

It died at ~44 MiB against a 50 MiB limit — the difference is page cache, the Python interpreter itself, and allocator overhead, all of which are charged to the cgroup.

**The receipt:**

```bash
cat $CG/memory.events
```

```
low 0
high 0
max 19
oom 1
oom_kill 1
oom_group_kill 0
```

| Counter | Meaning |
| ------- | ------- |
| `max 19` | hit the hard limit 19 times — each one triggering reclaim |
| `oom 1` | reclaim failed once; OOM handling invoked |
| `oom_kill 1` | one process was killed |

> 🔑 **`max` counting up without `oom_kill` is the healthy-but-tight signal.** The workload is constantly reclaiming — slow, but alive. That's the state to alert on *before* the kill.

## **`memory.high` — throttle instead of kill**

```bash
alloc60() {
  bash -c "echo \$\$ > $CG/cgroup.procs; exec timeout 20 python3 -c '
import time
b = bytearray(); t = time.time()
for i in range(60): b += bytearray(1024*1024)
print(\"allocated 60 MiB in %.2fs\" % (time.time()-t))
'"; echo "  rc=$?"
}

echo max > $CG/memory.max

echo max > $CG/memory.high;  echo max > $CG/memory.swap.max;  alloc60   # baseline
echo 30M > $CG/memory.high;                                    alloc60   # throttled
echo 0   > $CG/memory.swap.max;                                alloc60   # throttled, no swap
```

```
allocated 60 MiB in 0.03s      rc=0     ← baseline
allocated 60 MiB in 0.07s      rc=0     ← memory.high=30M: 2x slower, SURVIVED
                               rc=124   ← memory.high=30M + swap.max=0: never finished
```

Middle run: the process sailed past its 30 MiB soft limit and finished. `memory.events` shows `high 2582` — it was throttled 2582 times — and `oom_kill 0`. **Nothing died.**

> ⚠️ **Third run is the trap.** With `memory.high` set *and* swap disabled, the kernel has nowhere to reclaim anonymous memory to, so it throttles the process almost to a standstill — 20 s and still not done. `memory.high` needs somewhere for pages to go. Without swap, prefer `memory.max` (fail fast) over `memory.high` (hang slowly).

| | `memory.high` | `memory.max` |
| --- | --- | --- |
| Over the limit | throttle + reclaim | reclaim, then **kill** |
| Process survives | ✅ | ❌ |
| Use for | back-pressure, elastic workloads | a hard safety ceiling |

**Best practice: set both.** `high` slightly below `max` gives the workload a chance to shed memory before anything dies.

```bash
echo 400M > $CG/memory.high
echo 512M > $CG/memory.max
```

## **Always pin swap**

```bash
echo 0 > $CG/memory.swap.max
```

Without this, a container "under its limit" may actually be thrashing swap, and your `memory.max` no longer describes anything real. Kubernetes disables swap on nodes for exactly this reason.

```bash
cat $CG/memory.swap.current $CG/memory.swap.events
```

---

## **`memory.oom.group` — kill together**

By default the OOM killer picks **one** victim in the cgroup. For a multi-process app that usually leaves a broken half-alive container.

```bash
echo 1 > $CG/memory.oom.group     # kill every process in the cgroup, atomically
```

Then `memory.events` reports `oom_group_kill` instead of `oom_kill`. This is what you want for anything that isn't designed to lose a worker at random.

---

## **Observing memory**

```bash
cat $CG/memory.current           # bytes charged now
cat $CG/memory.peak              # high-water mark since creation
head -12 $CG/memory.stat         # the breakdown
cat $CG/memory.pressure          # PSI: how much time is lost stalling
```

```
some avg10=0.00 avg60=0.00 avg300=0.00 total=705
full avg10=0.00 avg60=0.00 avg300=0.00 total=705
```

**PSI (`memory.pressure`)** is the metric worth alerting on: `some avg10` is the % of the last 10 s in which *at least one* task stalled waiting for memory. It rises **before** things start dying, unlike `memory.current` which looks fine right up to the kill.

```bash
# force reclaim without killing anything (kernel >= 5.19)
echo 10M > $CG/memory.reclaim
```

## **Where this shows up in Kubernetes**

```yaml
resources:
  requests: { memory: "256Mi" }    # scheduling + memory.low-ish protection
  limits:   { memory: "512Mi" }    # -> memory.max = 536870912
```

* Exceed the limit → **OOMKilled**, container restarts, `restartCount` increments
* `kubectl describe pod` → `Last State: Terminated, Reason: OOMKilled, Exit Code: 137` (128 + SIGKILL)
* Requests ≠ limits → **Burstable** QoS; equal → **Guaranteed**; neither → **BestEffort** (killed first under node pressure)

**Find the real numbers on a node:**

```bash
PID=$(sudo crictl inspect <id> | jq .info.pid)
CG=/sys/fs/cgroup$(sudo cat /proc/$PID/cgroup | cut -d: -f3)
cat $CG/memory.max $CG/memory.current $CG/memory.events
```

> 💡 **Exit code 137 with no application error in the logs = OOM kill.** Check `memory.events` for `oom_kill` before you go looking for a bug in the code.
