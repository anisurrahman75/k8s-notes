# **4. PID 1 Is Special**

← [3.mount-proc.md](3.mount-proc.md) | next → [5.reaping.md](5.reaping.md)

---

The kernel treats PID 1 of **any** namespace differently from every other process.

| Behaviour                            | PID 1                                                       | Normal process     |
| ------------------------------------ | ----------------------------------------------------------- | ------------------ |
| Default signal actions               | **Disabled** — unhandled `SIGTERM`/`SIGINT` etc. are dropped | Terminate          |
| `SIGKILL`/`SIGSTOP` from **outside** | Allowed, but only from an ancestor namespace                | Allowed            |
| Orphaned processes                   | **Reparented to it** — it must reap them                    | Reparented to init |
| Death                                | **Kills the whole namespace**                               | Nothing special    |

---

## **Demo: PID 1 ignores signals it doesn't handle**

```bash
unshare -Urpf --mount-proc bash -c '
  sleep 100 & C=$!
  kill -TERM 1
  echo "PID 1 still alive after SIGTERM: $$"
  kill -9 $C
'
```

```
PID 1 still alive after SIGTERM: 1
```

A normal process would be dead. PID 1 isn't, because the kernel **removes the default action** for every signal PID 1 hasn't explicitly installed a handler for. If it registers a handler, the signal is delivered normally.

**Same from the host**, using the child's host PID:

```bash
unshare -Urpf --mount-proc sleep 100 & W=$!; sleep 0.6; C=$(pgrep -P $W)

kill -TERM $C; sleep 0.5
ps -p $C >/dev/null && echo "SIGTERM ignored by PID1 (still alive)"

kill -KILL $C; sleep 0.5
ps -p $C >/dev/null 2>&1 || echo "SIGKILL worked"
```

```
SIGTERM ignored by PID1 (still alive)
SIGKILL worked
```

`SIGKILL` and `SIGSTOP` from an **ancestor** namespace are the exception — they always work. That is how a runtime guarantees it can always tear down a container.

---

## 🔥 **This is *the* Kubernetes gotcha**

Your app runs as PID 1 in its container. `kubectl delete pod` sends `SIGTERM`.

> If your app does not **explicitly install a SIGTERM handler**, the kernel discards the signal. Nothing shuts down. 30 seconds later `terminationGracePeriodSeconds` expires and the kubelet sends `SIGKILL` — no graceful drain, dropped connections, possibly corrupt state.

**And there is a second trap right next to it:**

```dockerfile
ENTRYPOINT ["sh", "-c", "myapp"]   # ❌ sh is PID 1, and sh does NOT forward signals
ENTRYPOINT ["sh", "-c", "exec myapp"]   # ✅ myapp replaces sh, becomes PID 1
ENTRYPOINT ["myapp"]                    # ✅ best — no shell at all
```

```dockerfile
ENTRYPOINT ["/entrypoint.sh"]      # entrypoint.sh must end with:  exec myapp "$@"
```

**Checklist for any containerized service:**

| Check | |
| ----- | --- |
| App installs a `SIGTERM` handler and drains | ✅ |
| Entrypoint uses `exec` or JSON-array form | ✅ |
| `ENTRYPOINT ["sh","-c","app"]`, shell-form `CMD app` | ❌ |
| Long shutdown? raise `terminationGracePeriodSeconds` | ⚙️ |

---

## **Killing PID 1 Kills the Namespace**

When PID 1 exits, the kernel `SIGKILL`s **every remaining process in that namespace** and tears it down.

```bash
cat > /tmp/marker.sh <<'EOF'
#!/bin/sh
exec sleep 4242
EOF
chmod +x /tmp/marker.sh

unshare -Urpf --mount-proc bash -c '/tmp/marker.sh & /tmp/marker.sh & sleep 0.4; kill -9 1'
sleep 1
echo "survivors: $(pgrep -f -x 'sleep 4242' | wc -l)"
```

```
survivors: 0
```

Both children were killed by the **kernel**, not by the script. Nothing had to track them.

> 🔑 This guarantee is what makes containers cleanly disposable: **you cannot leak processes out of a PID namespace.** Kill the container's init and the whole tree goes with it.

**Contrast:** a plain `chroot` or a bare setuid sandbox has no such property — orphans there get reparented to the host's systemd and live forever. It is why "just chroot it" is not a sandbox.

---

## **Why `exit` from your sandbox shell feels so clean**

```bash
unshare -Urpf --mount-proc bash
sleep 3000 &
sleep 3000 &
exit                       # bash was PID 1
```

Back on the host:

```bash
pgrep -f -x 'sleep 3000' | wc -l
```

```
0
```

Same mechanism. This is also why a crashed PID 1 in Kubernetes takes the whole container down instead of leaving a half-dead pod full of orphans.
