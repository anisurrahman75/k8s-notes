## **Lifetime**

> A namespace is **destroyed when its last member process exits** — unless something holds a reference to it.

Three things keep one alive:

1. **A process** is a member
2. **An open file descriptor** on `/proc/PID/ns/X`
3. **A bind-mount** of `/proc/PID/ns/X` somewhere on the filesystem

### Demo: watch one die

```bash
lsns -t net | wc -l                       # baseline
unshare -Urn --fork sleep 5 &
sleep 1;  lsns -t net | wc -l             # +1, the sandbox's netns
sleep 6;  lsns -t net | wc -l             # back to baseline — reaped automatically
```

Nothing had to clean up. No daemon, no reference counting on your side — the kernel frees it when the last member leaves.

## **Pinning**

Option 3 above is how every real tool keeps namespaces around with no process in them:

```bash
sudo mkdir -p /run/netns
sudo touch /run/netns/persistent                        # an empty file as the mount point
sudo mount --bind /proc/$PID/ns/net /run/netns/persistent
# the namespace now survives even if $PID dies

sudo nsenter --net=/run/netns/persistent -- ip link     # enter it via the pinned path
sudo umount /run/netns/persistent                       # release; namespace is freed
```

That is literally all `ip netns add` does:

```bash
sudo ip netns add demo
ls -l /run/netns/            # the pin file appears
sudo ip netns exec demo ip link
sudo ip netns del demo       # umount + remove
```

> 💡 This also explains a common confusion: **`ip netns list` cannot see Docker's namespaces.** Docker pins under `/var/run/docker/netns/` instead of `/run/netns/`. Symlink or bind-mount them into `/run/netns/` and `ip netns` finds them.

## **Nesting**

Namespaces form a tree. Nesting is allowed and cheap — user namespaces up to 32 levels deep, other types bounded by `/proc/sys/user/max_*_namespaces`.

```bash
unshare -Ur --fork --uts bash -c '
  hostname outer
  unshare --uts --fork bash -c "hostname inner; echo \"level 2: \$(hostname)\""
  echo "level 1: $(hostname)"
'
```

```
level 2: inner
level 1: outer
```

Note the inner `unshare` needed **no `-U`** — it inherited the capabilities granted by the outer user namespace. This is how Docker-in-Docker, KinD nodes, and `systemd-nspawn` inside a container all work.

**Check the limits:**

```bash
cat /proc/sys/user/max_pid_namespaces
cat /proc/sys/user/max_mnt_namespaces
cat /proc/sys/user/max_user_namespaces
```

Reaching one of these gives `unshare: Operation not permitted` or `ENOSPC` — a classic symptom on nodes running thousands of short-lived pods.

## **Ownership**

Every **non-user** namespace is *owned by* the user namespace that was active when it was created.

```
   user ns (yours, uid 0 -> 1000)
        │ owns
        ├── mount ns
        ├── pid ns
        ├── uts ns
        └── net ns
```

That ownership link is what makes rootless containers possible: your fake root has real authority over the namespaces its own user namespace owns, and none at all over the host's.

**Query it:**

```bash
unshare -Ur --fork --uts sleep 60 &
sleep 1; PID=$(pgrep -x sleep | tail -1)
lsns -o NS,TYPE,PID,COMMAND -p $PID
readlink /proc/$PID/ns/user       # the owning user namespace
```

### The one-way rule

> **An ancestor namespace can see and act on its descendants. A descendant can neither see nor act on its ancestors.** There is no sibling visibility either.

This is why:

* the host can `kill` any process in any container, but a container cannot signal the host
* `nsenter` from the host into a container works, and the reverse is impossible
* nested containers can be inspected from the node, at every level
