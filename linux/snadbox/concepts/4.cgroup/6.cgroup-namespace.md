# **6. The cgroup Namespace**

← [5.pids.md](5.pids.md) | next → [7.systemd-and-k8s.md](7.systemd-and-k8s.md)

---

## **The one thing it does**

> A cgroup namespace makes the process's **current cgroup appear as `/`**.

It does **not** limit anything. It is purely about hiding your position in the tree — the same "different view of a global resource" idea as every other namespace ([../1.namespaces/](../1.namespaces/README.md)).

---

## **Demo: the path disappears**

```bash
# on the host
cat /proc/self/cgroup
```

```
0::/user.slice/user-1000.slice/user@1000.service/session.slice/org.gnome.Shell@wayland.service
```

```bash
# inside a cgroup namespace
unshare -UrC bash -c 'cat /proc/self/cgroup'
```

```
0::/
```

Same cgroup, same limits, same enforcement — only the *name* changed.

**With a real cgroup in play:**

```bash
U=$(id -u); CG=/sys/fs/cgroup/user.slice/user-$U.slice/user@$U.service/demo.slice
mkdir -p $CG

bash -c "echo \$\$ > $CG/cgroup.procs
         echo 'host view: ' \$(cat /proc/self/cgroup)
         unshare -UrC --fork bash -c 'echo \"ns view:   \$(cat /proc/self/cgroup)\"'"
```

```
host view:  0::/user.slice/user-1000.slice/user@1000.service/demo.slice
ns view:    0::/
```

## **Why it exists — three reasons**

### 1. Information leak

Without it, a container reads `/proc/self/cgroup` and learns its Kubernetes pod UID, namespace, and container ID, plus the node's whole cgroup layout:

```
0::/kubepods.slice/kubepods-burstable.slice/kubepods-burstable-podf4c8....slice/cri-containerd-9a3f....scope
```

That is the host's internal topology, handed to anything running inside.

### 2. `/sys/fs/cgroup` becomes mountable and correct

Inside a cgroup + mount namespace, mounting cgroup2 gives you **your own subtree at the root** — so tools inside the container see a sane hierarchy instead of the node's:

```bash
unshare -UrmC bash -c 'mkdir -p /tmp/cg && mount -t cgroup2 none /tmp/cg && ls /tmp/cg | head -8'
```

```
cgroup.controllers
cgroup.events
cgroup.freeze
cgroup.kill
cgroup.max.depth
cgroup.max.descendants
cgroup.pressure
cgroup.procs
```

> ⚠️ **You need `-m` too.** `unshare -UrC` alone cannot mount cgroup2 — it has no mount namespace to mount into:
>
> ```bash
> unshare -UrC bash -c 'mkdir -p /tmp/cg && mount -t cgroup2 none /tmp/cg'
> ```
> ```
> mount: /tmp/cg: permission denied.
> ```

### 3. Migration and nesting

A checkpoint/restore (CRIU) or a nested container manager can move a cgroup subtree elsewhere in the host tree and the processes inside never notice — their paths are all relative to their own root.

## **How runtimes use it**

```
HOST                                           CONTAINER'S VIEW
/sys/fs/cgroup/
└── kubepods.slice/
    └── kubepods-burstable.slice/
        └── ...pod<uid>.slice/
            └── cri-containerd-<id>.scope/  ══► /
                ├── memory.max                  ├── memory.max
                ├── cpu.max                     ├── cpu.max
                └── cgroup.procs                └── cgroup.procs
```

Same files, same limits, no host paths exposed. `docker run` and every CRI runtime enable this by default.

**Verify on any running container:**

```bash
docker run --rm alpine cat /proc/self/cgroup
```

```
0::/
```

## **The `nsdelegate` mount option**

```bash
findmnt -no OPTIONS /sys/fs/cgroup
```

```
rw,nosuid,nodev,noexec,relatime,nsdelegate,memory_recursiveprot
```

`nsdelegate` makes the kernel treat a cgroup namespace root as a **delegation boundary**: processes inside cannot be migrated to cgroups outside their namespace root, even if the cgroupfs permissions would otherwise allow it. It is what makes "hand a container its own subtree" actually safe.

---

## **What it does NOT do**

| Misconception | Reality |
| ------------- | ------- |
| "It limits resources" | No — limits come from `memory.max` etc. It only renames paths. |
| "It hides the limits from the container" | No — the container reads its own `memory.max` fine (and should). |
| "It stops escaping to a parent cgroup" | That's `nsdelegate` + filesystem permissions, not the namespace itself. |

> 🔑 **The cgroup namespace is cosmetic-but-important**: it prevents an information leak and makes in-container tooling work. All the *enforcement* is in the controller files from pages [3](3.memory.md)–[5](5.pids.md).

---

## **Quick reference**

```bash
unshare -UrC  bash                  # cgroup namespace only
unshare -UrmC bash                  # + mount ns, so you can mount cgroup2
mount -t cgroup2 none /sys/fs/cgroup

cat /proc/self/cgroup               # 0::/ means you're in one
readlink /proc/PID/ns/cgroup        # compare inodes
lsns -t cgroup                      # list them all
```
