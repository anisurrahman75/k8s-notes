# **3. Why `--mount-proc` Is Mandatory**

← [2.fork-rule.md](2.fork-rule.md) | next → [4.pid1-semantics.md](4.pid1-semantics.md)

---

## **The rule**

`ps`, `top`, `pgrep`, `htop` do not ask the kernel about processes. They **read `/proc`**.

A new PID namespace does not automatically get a new `/proc`. You inherit the host's mount table, so `/proc` is still the **host's** procfs, and every userspace tool keeps reporting the host.

---

## **Demo: the leak**

```bash
unshare -Urpf bash -c 'echo "my pid: $$"; echo "ps sees: $(ps ax | wc -l) procs"'
```

```
my pid: 1
ps sees: 690 procs      ← the whole host!
```

Look carefully: **the kernel isolation is already perfect.** `$$` is 1. The PID table is correct. What's wrong is only the *view* that `ps` is reading.

## **Demo: the fix**

```bash
unshare -Urpf --mount-proc bash -c 'echo "my pid: $$"; echo "ps sees: $(ps ax | wc -l) procs"'
```

```
my pid: 1
ps sees: 5 procs
```

---

## **What `--mount-proc` actually does**

It is shorthand for two things:

1. also create a **mount namespace** (`-m`), so the change doesn't affect the host
2. `mount -t proc proc /proc` inside it

Do it by hand and the result is identical:

```bash
unshare -Urpfm bash -c 'mount -t proc proc /proc; ps ax | wc -l; findmnt -no TARGET,SOURCE /proc'
```

```
4
/proc  proc
/proc  proc
```

Two `/proc` rows because the new procfs is **stacked on top of** the host's, not replacing it. The one on top wins; the one underneath is inaccessible but still mounted. This is normal and is what `--mount-proc` does too.

> ⚠️ **Never do this without `-m`.** `mount -t proc proc /proc` in the host mount namespace would replace the *host's* `/proc` with your namespace's view — and break every process on the machine.

---

## **The generalisable lesson**

> **Kernel isolation and the filesystem view are separate concerns.**

The PID namespace isolated the kernel's PID table immediately and correctly. The `/proc` leak was purely a **userspace view** problem, fixed by a mount.

This pattern repeats everywhere:

| Namespace | Kernel does the isolation | ...but userspace needs a mount/setup too |
| --------- | ------------------------- | ---------------------------------------- |
| PID       | own PID table             | remount `/proc`                          |
| Cgroup    | own cgroup root           | remount `/sys/fs/cgroup` ([../4.cgroup/6.cgroup-namespace.md](../4.cgroup/6.cgroup-namespace.md)) |
| Network   | own netstack              | mount its own `/sys/class/net`           |
| User      | own UID map               | its own `/etc/passwd` in the rootfs      |

**This is why PID and mount namespaces are always used together.** A PID namespace without a mount namespace is half a sandbox. Continue in [../3.mount/](../3.mount/README.md).

---

## **Verifying which `/proc` you're looking at**

`readlink /proc/self` returns the reader's PID **as procfs sees it**. Compare a leaking sandbox against a correct one:

```bash
echo "leak case:"
unshare -Urpf              bash -c 'echo "shell=$$; procfs says $(readlink /proc/self)"'
echo "fixed case:"
unshare -Urpf --mount-proc bash -c 'echo "shell=$$; procfs says $(readlink /proc/self)"'
```

```
leak case:
shell=1; procfs says 444468      ← a HOST pid — /proc is the host's
fixed case:
shell=1; procfs says 2           ← a namespace pid — /proc is ours
```

> 🔎 **One-line diagnostic:** if `readlink /proc/self` gives a big number while `$$` is small, your `/proc` belongs to a different namespace than your process. That's a missing `--mount-proc`.
